The MoonBit tutorial currently shows older example tool versions. This repository pins the versions actually tested together. This matters because the wit-bindgen project explicitly warns that MoonBit string, byte, and array ABI changes can allow mismatched generated bindings to compile and then fail at runtime.

Repeated `wit-bindgen 0.63.0` invocations were also observed to reorder semantically equivalent generated helper declarations. That changes the binary SHA-256 even when WIT and plugin logic are unchanged. Generated bindings are therefore checked in, and `wit/bindings.lock` avoids needless regeneration when the WIT digest and generator version already match. `MOONVCS_FORCE_REGENERATE=1 ./scripts/regenerate-bindings.sh` is a maintenance operation: its generated diff and all manifest digests must be reviewed before acceptance.

## Backend and integration choice

| Route | Actual result | Decision |
|---|---|---|
| MoonBit `wasm` → `wasm-tools component embed` → `component new` | compile, Component validation, and Wasmtime calls pass | selected |
| MoonBit `wasm-gc` with the same generated bindings | MoonBit check/build pass, but componentization fails because `evaluate` is not found as an interface export | rejected for phase 1 |
| MoonBit JS or native backend | does not produce the core Wasm artifact required by this pipeline | not applicable |
| hand-written core-Wasm ABI | possible, but would duplicate canonical ABI lifting/lowering and string/list handling | rejected in favor of generated bindings |

The selected path follows the MoonBit and wit-bindgen documented flow and has the smallest custom ABI surface.

## WIT contract

The authoritative interface is `wit/policy.wit`. It uses only WIT records, lists, options, enums, and a variant accepted by the installed generator.

`policy-request` includes the commit message, staged paths and bytes, and exact granted capability names. It also reserves hook and future object-ID fields already needed by MoonVCS. `policy-result` contains a decision and structured diagnostics.

The decision variant is `pass | reject | error(string)`. Reject reasons are structured diagnostics rather than a single string payload, allowing stable rule codes, severity, and paths. Thus `Reject("forbidden-demo detected")` is represented as `reject` plus a diagnostic whose message is `forbidden-demo detected`.

## Build path

Bindings are generated by `wit-bindgen moonbit` and checked in under the binding-input lock described above. The implemented stub is compiled by MoonBit's `wasm` backend. `wasm-tools component embed` attaches the WIT metadata, `component new` produces the Component binary, and `wasm-tools validate --features component-model` validates it. The build then checks the component SHA-256 against its reviewed manifest.

The Rust host uses `wasmtime::component::bindgen!` against the same WIT package. It creates a Component `Linker`, instantiates the component, constructs `PolicyRequest`, calls `evaluate`, and serializes the lifted `PolicyResult` as JSON.

## Isolation evidence

The following command is also asserted by `scripts/test.sh`:

```bash
.toolchains/cargo/bin/wasm-tools component wit \
  target/components/hello-policy.component.wasm
```

The extracted world contains only:

```wit
world root {
  export moonvcs:policy/evaluator@0.1.0;
}
```

There are no component imports. The host also instantiates with an empty Component `Linker`; it supplies no WASI, filesystem, network, environment, clock, random, or shell interface.

`granted-capabilities` is explicit request data, not ambient authority. The host calculates requested ∩ repository-allowed ∩ host-supported capabilities before execution. A denied manifest request is a host authorization failure before plugin execution; this report does not describe it as a fabricated guest `CapabilityDenied` result.

## Exception and resource behavior

The required normal, rejection, invalid-input, and Trap paths are automated. The suite additionally proves fail-closed handling for infinite-loop fuel exhaustion, denied linear-memory growth, and oversized output. Fuel, epoch timeout, Store memory, aggregate input, and result-output limits are implemented rather than deferred.

Remaining limitations are documented in `KNOWN_LIMITATIONS.md`. In particular, Store limits do not account for every host/JIT allocation, and an epoch-only timeout test is still pending.

```bash
./scripts/regenerate-bindings.sh
```

```bash
host/target/debug/moonvcs-policy-host \
  --component target/components/hello-policy.component.wasm \
  --manifest plugins/hello-policy/plugin.toml \
  --policy examples/hello-policy.toml \
  --message "add safe configuration" \
  --file examples/clean.txt

host/target/debug/moonvcs-policy-host \
  --component target/components/hello-policy.component.wasm \
  --manifest plugins/hello-policy/plugin.toml \
  --policy examples/hello-policy.toml \
  --message "commit forbidden-demo" \
  --file examples/clean.txt
```
